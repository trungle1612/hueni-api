# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Rails 8 backend for **hueni** (`https://hueni.me`, private repo `trungle1612/hue-ni`, usually checked out at `../hue-ni`), a static React travel guide for Huế. It provides:

1. `GET /v1/vacancy` — public JSON of free homestay rooms today, consumed by hueni's "Phòng trống" tab.
2. `/admin` — owner admin (Hotwire): owners manage rooms, calendar feeds and bookings; admins manage user accounts (homestay data only where they are members).
3. iCal sync pulling bookings from owners' Airbnb / Booking.com calendars: `CalendarFeed#sync` + `SyncCalendarFeedJob` (hourly schedule is #15).

**Design spec:** `../hue-ni/docs/superpowers/specs/2026-09-26-hueni-api-design.md` (lives in the hue-ni repo). Work is tracked as GitHub issues grouped under epics #12 (Step 1), #16 (Step 2), #24 (Step 3), #28 (Step 4). **Issue bodies are newer than the spec** where they differ — see "Deviations" below. If code, issue and spec disagree, ask.

## Commands

rbenv shims are not on PATH in non-interactive shells; prefix commands with `export PATH=~/.rbenv/shims:$PATH &&` (system Ruby is 2.6).

```bash
bin/setup                                  # gems + DB
bin/dev                                    # http://localhost:3000 (server + Tailwind watcher)
bin/rails test                             # all non-system tests
bin/rails test test/models/vacancy_test.rb      # one file
bin/rails test test/models/vacancy_test.rb:12   # one test by line
bin/rails test:system
bin/rubocop                                # rubocop-rails-omakase
bin/brakeman --no-pager                    # runs with --ensure-latest: fails if a newer brakeman exists → bundle update brakeman --conservative
bin/rails places:import[path]              # upsert places from hueni's homestay.json (default db/places/homestay.json)
```

CI (`.github/workflows/ci.yml`) runs brakeman, bundler-audit, importmap audit, rubocop, `bin/rails db:test:prepare test` and `test:system` on every PR.

## Architecture

**Data model** (`db/schema.rb`): `places` → `rooms` → `bookings`, plus `calendar_feeds` (room → feed → its imported bookings) and `place_memberships` (users ↔ places, many-to-many).

- `places.slug` = hueni's `Place.id`. Other place columns (address, phone, rating, lat/lng, …) are a **read-only copy** of hueni's `homestay.json`, overwritten by `places:import`. hueni stays the source of truth; never edit them here.
- `bookings`: `end_date` is **exclusive** (checkout day is free). `status` = `confirmed` | `cancelled` (no Giữ chỗ since #127, like the Zalo app; old `hold` rows were confirmed, `hold` survives only in paper_trail history); `source` = `manual` | `ical`. Values are enforced by DB check constraints *and* `enum ..., validate: true`. Cancelled rows are kept as history, not deleted. Status changes go through the AASM events on `Booking` (`cancel`, `reopen` = Khôi phục; `Booking#update_with_status` for the admin form) — hang future side effects (notifications, tracking) there. The iCal sync writes `status` directly: its bookings are created confirmed and never transition. Prices: `bookings.price` / `weekend_price` are the quote snapshotted from the room on create (#120, `Booking#price_on`); `bookings.deposit` = Đã cọc; a manual booking not checked in without a deposit is *Chưa cọc* (`awaiting_deposit?`, amber `!` bar on the calendar).
- `Booking.occupying(from, to)` / `blocking_on(date)` (confirmed bookings covering the nights, minus nights from the check-out day of a checked-out booking, plus through today for a guest still in after the departure day — `Booking#occupied_until`) is the single definition of "room occupied" — vacancy, the overlap rule and calendar conflicts build on it. `overlapping` is plain date overlap (what the timeline draws).
- A manual confirmed booking can't overlap another blocking booking on its room (validation). The booking form's live "còn trống / trùng lịch" line (`GET bookings/availability`) runs the same validations via `Booking#date_problems` — keep date rules there, not in the view. iCal bookings skip it (the OTA already sold the nights); an iCal booking overlapping a manual one is shown on the calendar as a conflict for the owner to resolve.
- The iCal sync never deletes a checked-in stay: missing from the feed → `removed_from_feed_at` (badge "OTA đã huỷ"), cleared if it comes back. Check-in is refused while another guest is in the room. Check-in records a fact: it saves without validation (except early check-in, which moves dates). `Booking.arrival_date` (yesterday until `Booking::LATE_ARRIVAL_UNTIL` = 06:00) lets after-midnight arrivals be checked in and keeps them in Hôm nay / the room board; vacancy keeps calendar days.
- Check-in/out are timestamps (`bookings.checked_in_at` / `checked_out_at`) beside `status`, not statuses: the iCal sync rewrites `status` on every run. `Booking#check_in` / `#check_out` return true/false (reason in `errors[:base]`); check-out marks the room `dirty` and frees the remaining nights (dates stay as history; the admin can no longer edit it — locked in `Admin::BookingsController#update` + the form, not the model, so the iCal sync still updates it); check-in before `start_date` (Nhận phòng sớm, manual only, room free from today) moves `start_date` to today. `rooms.housekeeping` (`clean` | `dirty` | `maintenance`): clean/dirty are independent of vacancy; `maintenance` = Bảo trì (#121, staff too, `Admin::RoomsController#maintenance`, not while a guest is in) with `maintenance_reason` + `maintenance_until` blocks the room from today through that day (`Room#maintenance_on?`): out of `Vacancy`, new/moved manual bookings refused (`Booking#in_maintenance?`), no check-in or move into it, striped days on the calendar, bookings already there shown as conflicts. "Xong bảo trì" = `clean`; `Room.end_maintenance` (daily 00:05, `config/recurring.yml`) turns an expired one into `dirty`. `RoomDay.for(rooms)` is the single "room state today" (off / leaving / occupied / maintenance / arriving / free) for the dashboard board and the homestay page; `Admin::StaysHelper` renders its badges and the Check-in / Check-out / Dọn xong buttons. Staff can do all of it; no-show = cancel the booking with a note. Owners (not staff) can undo a check-in / check-out the same day (`Booking#undo_check_in` / `#undo_check_out`, "Hoàn tác" on the booking page). Room move: `Booking#move_to(room)` (in-house manual guests, free room of the same homestay, old room → dirty; staff too). Check-in requires a head count when the booking has none (enforced in `Admin::BookingsController#check_in`; `Booking#check_in(guests:)`). `bookings.declared_at` = "Đã khai báo lưu trú" (`Booking#declare`), a reminder badge only.

**Vacancy** (`app/models/vacancy.rb`): `Vacancy.on(date)` computes `{ slug => { left:, max_guests: } }`; `Vacancy.cached` wraps it in `Rails.cache` under `["vacancy", Date.current]` for 5 min. Every `Place`, `Room`, `Booking` and `CalendarFeed` has `after_commit { Vacancy.bust }`. **Bulk writes that skip callbacks (`delete_all`, `upsert_all`, the iCal sync) must call `Vacancy.bust` themselves.**

**Activity log** (#46): paper_trail writes a `versions` row for allowlisted changes on `Room`, `Booking`, `CalendarFeed` (`has_paper_trail only: …`, meta `place_id` / `room_id`). `whodunnit` = user id in admin requests (`ApplicationController#user_for_paper_trail`), the feed's provider during `CalendarFeed#sync`, nil → "Hệ thống". `calendar_feeds.url` is `skip`ped. Writes that skip callbacks (`update_columns`, `delete_all`) are not logged — use `save!(validate: false)` when a change must be logged without validation. `Admin::ActivityHelper` renders versions as Vietnamese lines on `/admin/places/:slug/activity` and the "Lịch sử" blocks (owners/admins only).

**Sync log** (#92): every `CalendarFeed#sync(trigger:)` (`hourly` from `SyncCalendarFeedJob`, `manual` = Đồng bộ ngay, `added` = Thêm kênh) writes a `SyncRun` (ok/error, created/updated/removed counts, duration) outside the bookings transaction, so failures are logged too. Admin-only page `/admin/dong-bo` (`Admin::SyncRunsController`) — it names homestay + room (agreed exception to #85), never guests, dates or feed URLs. `SyncRun.prune` (daily, `config/recurring.yml`) keeps 30 days.

**Report** (#77): `Report.new(place, month)` computes the owner-only `/admin/places/:slug/report?month=YYYY-MM` page (occupancy, estimated revenue = nights × current `rooms.price`, average price, average stay, channel mix, cancellation rate incl. OTA cancellations from paper_trail `destroy` versions; plain Vietnamese labels, no ADR/RevPAR jargon — #117). Nights sold use `Booking#occupied_until`. The current month runs 1st → today (`Report#last`), compares with the same days of last month, and lists confirmed nights after today as `ahead`.

**Public API** (`app/controllers/v1/`): controllers inherit `ActionController::API`, not `ApplicationController` (which has `allow_browser :modern` and would block curl/uptime checks). CORS is a hand-set `Access-Control-Allow-Origin` for `https://hueni.me` and `http://localhost:5173` only — no `rack-cors`. `/v1/*` must never expose guest fields, feed URLs or `uid`s; the request test asserts this.

**Auth & admin:** Rails 8 authentication generator (`Authentication` concern in `ApplicationController`, DB-backed `sessions`) — every controller requires login unless it calls `allow_unauthenticated_access`. `users.role` = `admin` | `user`; rights per homestay come from `place_memberships.role` = `owner` | `staff` (a homestay keeps at least one owner — model rule). **Admins run accounts, not homestays (#85):** `users.role = admin` adds only Người dùng (accounts + memberships at every homestay) and, on Tổng quan, a list of all homestays with members and failing-feed counts. Everything inside a homestay follows the membership, for admins too — to help an owner, an admin adds themselves as a member. Authorization is `User#allowed_to?(action, place)`, membership-only: `:manage` = owner (incl. Hoàn tác); `:operate` = front-desk work (check-in/out, no-show, room move, lưu trú, Dọn xong) for owner or staff. Controllers call `authorize!(action, place)` after the scoped lookup, views use the `allowed_to?` helper. Owner-only: rooms index (menu Phòng, every homestay you own — room setup lives there, the homestay page is the daily board)/new/create/edit/update, feeds create/destroy, members (`Admin::MembersController`). Staff: dashboard, homestay page (no prices), calendar, bookings, feed sync. Admin controllers inherit `Admin::BaseController` (scoping in #18). The admin menu is one list, `ApplicationHelper#admin_menu_items`, rendered as a bottom dock on phones and a sidebar on `lg+`; `path: nil` items show as "Sắp có".

**Login (#97): owners and staff log in with Zalo only** (`omniauth-zalo2`, `ZaloSessionsController`, `users.zalo_id`); **phone + password is admin-only**, enforced in `SessionsController#create` (non-admin → same message as a wrong password). No email or mailer. A Zalo id is bound via the one-time link, by a logged-in user ("Liên kết Zalo", `?link=me`), by the Zalo phone (#98), or by an approved registration: an unknown Zalo login keeps its id in `session[:registration]` (30 min, never from params) and goes to `/dang-ky` (`RegistrationsController`) → `RegistrationRequest` (pending/approved/rejected, one pending per Zalo; the owner can correct a pending one in place, `?sua=1`) → Telegram ping (`NotifyRegistrationJob`, env `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`; name + homestay + link only, never phone/Zalo id) → an admin calls the homestay's hueni phone and approves in Người dùng (`Admin::RegistrationRequestsController`; `RegistrationRequest#approve!` creates the Zalo-linked user + owner membership, never for a homestay that already has an owner, and needs an `admin_note` when there is no hueni phone to call — `verifiable?`). A blank uid logs nobody in. `users.phone_number` is normalized to 10 digits starting with 0 (`+84 912 345 678` → `0912345678`); `normalizes` also rewrites values in `where(phone_number: …)`, so use raw SQL to match non-phone strings. Admins (`/admin/users`) and owners (Thành viên) create users and get a one-time link (`/dat-mat-khau/:token`, `generates_token_for :password_setup`, 7 days, invalidated by any password change) to send over Zalo: non-admins link Zalo there (`?link=token`, token kept in `session[:zalo_link_token]`; binding rotates the placeholder password, consuming the link), admins pick a password. "Tạo link liên kết Zalo" / "Tạo link đặt lại mật khẩu" = `User#reset_login!` (unlinks Zalo, locks the password, ends every session). The link is shown once via `flash[:setup_link]` (the layout renders only `notice` / `alert`). Zalo app id/secret: env `ZALO_APP_ID` / `ZALO_APP_SECRET` (Kamal secrets ← Actions secrets). Development uses the real Zalo app (keys in credentials `zalo.app_id` / `app_secret`, or env); `ZALO_FAKE=1 bin/dev` opts into a labelled fake picker; no keys → the button is disabled with a notice; tests use `OmniAuth.config.test_mode` and the shared `log_in(user)` helper. `bin/rails db:seed` loads made-up demo data in development (`db/seeds/development.rb`).

**Time:** `config.time_zone = "Asia/Ho_Chi_Minh"`. Always `Date.current` / `Time.current`. A Huế day starts at 17:00 UTC; tests use `travel_to`.

## Deviations from the spec (agreed, already in issues)

- `places` table with FKs instead of string `place_id` + `config/places.yml`.
- Bookings have `status` (confirmed/cancelled; Giữ chỗ removed in #127) and optional `guest_name`, `guest_phone`, `note`, quoted `price` / `weekend_price`, `deposit`.
- Rooms have `price` (VND/night, admin-only) and `photo_urls` (JSON array of http(s) URLs).
- Admin calendar (#21) is a per-place timeline (rooms × days); iCal bookings overlapping manual ones are shown as conflicts.

## Security invariants

- **This repo is public; hue-ni is private.** Never commit data copied from hue-ni (`db/places/*.json` is git-ignored). Test fixtures use made-up data.
- `calendar_feeds.url` embeds OTA tokens: never render it in `/v1/*`, keep `:url` in `filter_parameters`.
- SSRF: feed URLs must be http(s) and resolve only to public IPs (`CalendarFeed.public_ip?`), checked on save **and again at fetch time** (DNS rebinding).
- iCal sync failure must change no bookings; record `last_error` / `last_error_at` instead. `CalendarFeed#sync` fetches and parses *before* opening the transaction.
- Admin rule: every admin lookup goes through `Current.user.accessible_places / _rooms / _calendar_feeds / _bookings` (places the user is a member of — admins included). Never `Place.find` / `Room.find` etc. in admin controllers. Use `find` / `find_by!` (never `find_by`, which returns nil → 500). Never permit `place_id` / `room_id` / `calendar_feed_id` in params; build children through a scoped parent (`Current.user.accessible_rooms.find(params[:room_id]).bookings.build(...)`). Out of scope → `RecordNotFound` → 404. In scope but not allowed (staff on an owner-only action) → `Admin::BaseController::Forbidden` → 403 page. Each new admin page adds a request test that another owner's record returns 404; each owner-only action also tests staff → 403.

## Conventions

- All user-facing strings in Vietnamese, inline in views/controllers. Admin UI: server-rendered ERB + Turbo/Stimulus via importmap, **Tailwind 4 + daisyUI 5 (`autumn` theme only)** via `tailwindcss-rails`; daisyUI is the vendored `app/assets/tailwind/daisyui.mjs` (update by re-downloading; keep `@source not "./daisyui.mjs"` or every daisyUI class gets emitted). Mobile-first. The admin does not follow hueni's design.
- SQLite for everything (primary + Solid Queue/Cache/Cable). No Redis, no Postgres, no Node build.
- Prefer stdlib over new gems (e.g. `Resolv`/`IPAddr` for SSRF, `Net::HTTP`).
- HTTP in tests is blocked by WebMock (`webmock/minitest`, localhost allowed); stub every external request. Use public IP literals (e.g. `https://1.1.1.1/…`) for feed URLs so validation needs no DNS.
- Minitest 6: `stub`/`minitest-mock` are not available — swap collaborators directly (e.g. `Rails.cache = ActiveSupport::Cache::MemoryStore.new` with `ensure` restore; test env cache is `:null_store`).
- Unmerged migrations may be edited in place; once on `main`, add a new migration.
- One branch + PR per issue (`<issue>-<slug>`), PR body `Closes #N`. Never push to `main`.

## Deployment (#9, #10)

Kamal 2 → the project VPS; host/user come from `DEPLOY_HOST` / `DEPLOY_USER` (Actions secrets), never committed. `.github/workflows/deploy.yml` runs `bin/kamal deploy` after CI passes on `main` (or by hand: Actions → Deploy → Run workflow); image on GHCR (`ghcr.io/trungle1612/hueni-api`, pushed with `GITHUB_TOKEN`). kamal-proxy publishes only `127.0.0.1:8080` (`proxy.run` in `config/deploy.yml`) without TLS, `forward_headers: true`; the VPS's nginx serves `api.hueni.me` → `:8080` with certbot and sets `X-Forwarded-For` / `-Proto`. **Kamal must not take ports 80/443** — nginx serves hueni.me there. Production: `assume_ssl` + `force_ssl`, `config.hosts = ["api.hueni.me"]`, `/up` exempt from both. SQLite on host volume `/var/lib/hueni-api/storage` → `/rails/storage`. Backups: Kamal accessory `litestream` (`config/litestream.yml`) streams `production.sqlite3` only to R2 bucket `hueni-api-backup` (10 s sync, 7 days); `kamal deploy` does not restart it — `bin/kamal accessory reboot litestream` after changing its config/secrets. Restore steps in README → Backups. Local `bin/kamal` needs `.env` loaded (`set -a; source .env; set +a`) and a `KAMAL_REGISTRY_PASSWORD` (e.g. `$(gh auth token)`). The `deploy` user has no sudo (docker group only). The VPS cannot reach NTP: check `date -u` there if dates look off.
